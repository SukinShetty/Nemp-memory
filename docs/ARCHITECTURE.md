# How Nemp works

Nemp is **agentic memory that evolves with your work**. In Nemp Open v0.3.0, “agentic” describes the host agent executing memory instructions. It does not imply an autonomous learning service.

## Execution model

1. A user invokes a command, or the host loads the Nemp skill
2. The host agent reads the relevant Markdown instructions
3. The agent uses its filesystem tools to inspect and update local files
4. The command reports its result; later sessions can retrieve that context

The repository contains Markdown command/skill instructions, JSON plugin metadata, experimental hook instructions and documentation. It has no dedicated memory server, vector database, embedding pipeline or model runtime. Outcomes depend on the host following the instructions, permissions and data shape.

## The memory lifecycle

| Stage | Current mechanism | Boundary |
| --- | --- | --- |
| Capture | Explicit save; stack detection; experimental suggestions | Capture is not proof that a fact is correct |
| Structure | Keys, concise values, types, timestamps and agent metadata | Type inference is heuristic |
| Retrieve | Exact/partial keys, value search and keyword expansion | Current recall/context instructions read whole stores |
| Review | List, logs, health checklist, sync drift checks | No general factual-verification engine |
| Refine | Upsert a key; delete after confirmation; refresh exported context | No built-in version history or undo |

## Storage

| Location | Purpose |
| --- | --- |
| `.nemp/memories.json` | Project memories |
| `~/.nemp/memories.json` | Cross-project memories and preferences |
| `.nemp/MEMORY.md` | Human-readable index generated by supported commands |
| `.nemp/config.json` | Project settings such as `autoSync` |
| `.nemp/access.log` | Operations recorded by participating command instructions |
| `.nemp-pro/config.json` | Experimental activity/auto-export configuration; legacy path |
| `.nemp-pro/activity.log` | Experimental captured activity |
| `CLAUDE.md` | Optional exported project context, alongside user instructions |

There is no Nemp-hosted copy of these files in this build. Host/model handling is a separate boundary described in [Privacy](PRIVACY.md).

### Entry fields and format compatibility

A simplified entry looks like this:

```json
{
  "key": "api-style",
  "value": "Use REST for all APIs; GraphQL retired after the migration",
  "type": "decision",
  "tags": ["api"],
  "agent_id": "main",
  "created": "2026-10-01T08:00:00Z",
  "updated": "2026-10-01T09:00:00Z"
}
```

This shows an entry, not a guaranteed top-level file schema. Existing commands describe flat key/object maps, arrays, and a `{ "memories": [...] }` wrapper. Export explicitly handles the wrapper and a legacy key/object map; other command instructions are not fully normalized. Preserve existing files and test a copy before migrating formats. A versioned schema and migration need implementation and tests.

Some commands add `confidence`, `vitality` and `links` fields. These are instruction-driven metadata, not calibrated probabilities or evidence that the Pro engines run. Repeated access measures use, not truth. Rolling-window counters and scoring need stronger validation.

## Retrieval and context cost

`recall` and `context` load project/global memory and select results through exact matching, keywords and a synonym map. This requires no separate embedding service, but the host may read the entire store. There is no demonstrated bounded-context or token-savings guarantee. Recall/context may also update tracking metadata; they are not strictly read-only operations.

## Export and sync

- `/nemp:export` writes a Nemp-managed section to `CLAUDE.md` by default
- `--replace` replaces the whole file, including hand-written content
- Auto-sync runs as part of supported memory commands, not as a daemon
- `/nemp:sync` imports/reconciles selected context and checks some project-file drift
- Cross-tool export instructions exist experimentally; they are not a released round-trip integration

## Reliability boundaries to test next

- One schema across initialization, saving, retrieval, sync and export
- Atomic writes and coordination when several agents access a store
- Exact section boundaries so exports preserve surrounding instructions
- Hook registration/execution and capture permissions
- Complete operation logging and correctly maintained time windows
- Reversible edits/deletion, source provenance and evaluation fixtures

These are [release checks](RELEASE_CHECKLIST.md) and [roadmap work](ROADMAP.md), not guarantees of this documentation update.
